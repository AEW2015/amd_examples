# SCU35 PMC lab

Resolve the lab root as the directory containing `lab.py`, `hw/`, `fw/` and `evidence/`. Read its `README.md`, `AGENTS.md`, `docs/hardware.md` and `docs/audit.md`; no external personal workspace is required. Source/tool/build paths are configured through `config.json` or documented environment variables.

1. Start with `python lab.py verify` and the replay-first notebooks. Preserve the original captures and hashes. Default notebook execution must not access hardware.
2. For the vendor path use `lab.py build`: shared IPI → XSA → standalone `mb` BSP → ELF → implemented PDI. The PL MicroBlaze V is distinct from the dedicated PMC RISC-V processor.
   For the shared tutorial and Ethernet designs, verify 128 KiB local memory across both instruction/data BD address segments, the exported XSA/BSP, and the application linker script. At base zero this means high address `0x1FFFF` and linker `LENGTH = 0x20000`. A manually created platform was observed with only `8K` / `0x1FFF` / `0x2000`; optimization does not fix that configuration mismatch. Follow the [memory audit](../../docs/hardware.md#local-memory-audit) before changing a linker limit; update hardware/XSA/platform first when required.
3. For fastest resident payloads use `lab.py native`. The experimental independent firmware and JTAG/reference fixture are separate from the stock AMD PLM and secure-boot path. Check the actual ELF/PDI and owned memory layout.
4. `lab.py boot` uses fresh stateful HSS signing keys and creates unsigned/signed/encrypted variants of real designs. Never duplicate or rewind private signing state. Public all-zero AES roots are educational diagnostics, not secrecy or proof of another device's provisioning.
5. Hardware actions require task authorization. Use the exact SCU35 cable/part, configured matching client/server, local reservation and recovery image/hash. Execute one session at a time; preserve failures and independently verify recovery. No eFUSE or flash programming.
6. Runtime checks include exact SHA3/SHAKE/AES results, negative signature/tag tests, RNG smoke and PUF clear/regenerate/AES cycles. PUF keys/helper data remain inside owned volatile memory. No entropy or cryptographic qualification claim follows from a smoke test.
7. Timer provenance: current PL application uses AXI Timer at nominal 100 MHz, coherent 64-bit reads but 32-bit elapsed CMP fields. Native benchmark uses `mcycle`, referenced to the nominal PL clock. Boot captures predate the AXI Timer revision. JTAG and UART are outside operation timing.
8. Prefer public AMD documentation and the pinned public driver sources. UG1680 requires Design Security Lounge access; do not substitute Versal register recipes or invent public subsection URLs.
9. For actual Ethernet payloads, use the separate `ethernet/` application and its matching PDI/ELF/XSA, not the native/JTAG fixture. Read [the example](../../ethernet/README.md) and [dashboard lifecycle/timing](../../ethernet/DASHBOARD.md) for this mode. The dashboard retains the volatile configuration and board reservation until recovery. Its AES key is public diagnostic material. Hardened PMC DMA is present, but the delivered Ethernet Lite design has no streaming AXI DMA core. The [MAC/DMA upgrade](../../ethernet/DMA.md) remains unbuilt and its MAC license usability unconfirmed.
10. Continuous Ethernet traffic uses one request in flight; unpaced mode amortizes stats over 64 verified packets. Two-request short probes improved throughput, but a sustained run timed out; preserve that failure instead of treating the short rate as sustained. Keep network RTT, observed input payload rate, AXI Timer device intervals and native resident-buffer timing separate. LMS/HSS dashboard buttons/graphs inspect recorded native batches; this Ethernet firmware does not implement full LMS/HSS verification.
11. For lesson changes, edit `docs/presenter/`, regenerate with `scripts/refresh_presenter.py` and `scripts/build_site.py`, then run the site/link checks described in [publishing guidance](../../docs/site.md). Chapter 18 contains the complete Ethernet example. Keep static Pages content distinct from the locally running hardware dashboard, preserve dashboard server routes during report-link repair, and derive chapter counts from content rather than hardcoding them.

Update the local evidence/manifest only from actual artifacts. A build, positive timing slack, DONE status, successful manifest check and a complete correct payload run establish different gates. Report which OS/tool/hardware paths were actually exercised.
